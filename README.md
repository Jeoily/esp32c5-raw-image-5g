# ESP32-C5：5.2 GHz 实时残余误码传图

本项目独立于旧传图工程和 `esp32c5_fcs_probe`，两端均需烧录本文件夹的新固件。当前传输明文 RGB 像素，尚未加入 X 极化密钥或加密。

## 开始使用

1. 关闭旧传图界面、探测界面和占用串口的监视器。保持已经验证过的两块 ESP32-C5 与两块超表面 Y 极化接线。FPGA 使用你已验证的 Y 极化配置，本项目不修改 FPGA。
2. 双击本目录 `start_demo.bat` 打开界面。
3. 点击“刷新”，选择实际 Alice、Bob 串口；默认 COM3/COM4 仅为预填值，必须核对开发板。
4. 点击“编译并烧录Bob”，等待完成；再点击“编译并烧录Alice”，等待完成。不要在烧录期间拔线。
5. 点击“连接两端”。日志中应分别出现 `INFO Alice 40 … raw_image_v1` 和 `INFO Bob 40 … raw_image_v1`，界面提示两端就绪。如果没有回应，按两块板的复位键；错误或持续重启时保留“连接日志”。
6. 点击“选择图片”。最快模式建议尺寸上限 **256**、块间隔 **0 ms**、功率上限 **8 dBm**。图片等比缩放到 256×192 以内，不拉伸；也可选择 160 做更短的测试。
7. 点击“发送一次”。Bob 逐块显示实际接收的像素。新版默认0 ms，使用最多4块的流水窗口；大于0时恢复逐块确认和指定间隔。若发生本地队列丢弃，改用10、20或50 ms。实际耗时以界面统计为准，不承诺特定速度。
8. 先做一轮无遮挡测试，再发一轮并在中途遮挡数秒，然后移开。每轮只发送一次，各轮画面重新开始，不修补上一轮。
9. 结束后等待约 3 秒收尾，点击“结果目录”。也可中途点“停止”，保存已经收到的部分。

## 循环发送

连接两端并选择图片后，点击“循环发送”，自动重复发送所选图片。每轮采用新的会话号，Bob从空白接收状态逐块重建，不继承上一轮的像素；因此本轮缺失不会被上一轮的正确图像掩盖。统计每轮重新计数，结果按独立文件夹保存，settings.json包含循环轮次。

循环模式现在采用多轮并行收尾：Alice本轮发送结束后自动启动下一轮，不再固定等待3秒。上一轮仍在后台保留至少约3秒接收窗口，按会话编号处理迟到数据，事件队列排空后关闭；接收结果、原图和统计文件由单独的保存线程写入。下一轮开始后，旧轮次的数据只更新旧轮次归档，不让预览倒退，也不补入新图。

点击“停止”会取消后续轮次并停止当前发送，但继续完成已有接收收尾和后台保存。单次发送保留原有约3秒收尾。断开或关闭窗口时保存现有部分结果，尚未处理的串口数据可能不再纳入，结果标记链路中断。设备重启、发送失败或后台保存失败会停止循环。正常无线丢包或误码不会阻止下一轮。

为限制内存，待收尾轮次达到32或待保存任务达到8时暂缓启动下一轮，消化积压后恢复；不会为了追求连续而静默丢弃待保存轮次。计数为启动下一轮时的阈值，多个轮次同时到期可能暂时增加保存任务数。实时串口日志仍在接收处理中写入，磁盘过慢会影响处理速度。关闭窗口会等待已提交的保存任务结束。长时间循环会持续产生结果文件和日志。

只需重新打开界面，无需重新烧录。循环测试验证第二轮在第一轮收尾期间启动、迟到块进入正确归档且不污染当前图、RSSI跨轮保留以及停止后不再启动。无线发送仍有串口、命令和调度开销，这不是零间隔空口连续波或视频。

仅连接或打开界面不会主动发送图片。发射发生在点击“发送一次”或“循环发送”之后。

## 画面应如何理解

- 图像按从上到下、每行从左到右排列为 RGB888 字节流，每块 240 字节，即 80 个像素。块可能跨越行边界。
- Alice 每块只提交一次广播发送，不使用 TCP，不等待 Bob 确认，不因缺失或错误重发。
- Bob 保留可识别数据块的首次接收载荷，包括接收状态异常但仍能读到的载荷；载荷中的错误位直接变成错误颜色。
- 深灰色是尚未收到或无法可靠定位的数据块，不是人为生成的无线错误。开始阶段全部缺失，后续逐块填入；最终仍缺失的位置继续保持深灰色。
- 地址、会话号或定位头损坏时，该块不会被随意放入图像，表现为缺失。完全收不到无线信号时，通常表现为空缺，而不是必然出现雪花。
- 原图只用于左侧展示和诊断比较，不用于生成 Bob 接收画面。每轮新会话隔离旧包，重复包不修复首次收到的像素。
- 接收进度条表示**已收到字节的覆盖率**，不是发送完成度；存在丢失时，发送结束后也不会达到 100%。

这里展示的是 **Wi-Fi 物理层纠错之后仍残留的载荷错误**，不是绕过 ESP32 物理层编码的完全“无码”通信。此前 probe_v3 的遮挡实验已经捕获了错误载荷，但不能保证每次遮挡都出现同样的误码：轻度衰落可能仍正确，严重衰落可能直接丢包，绕射或泄漏也可能保持通信。

## 结果文件

界面Bob实时RSSI：显示最新可识别图像块的dBm值、近1秒样本的dBm算术均值和距更新时间。约每100 ms刷新；超过1秒未取得新块则显示“— / 未收到可识别新块”，不会把历史值冒充实时信号。循环中跨轮连续更新，不清空滚动窗口；停止且全部轮次收尾后标为非实时值。各轮文件中的RSSI统计仍互相独立。

仅统计Bob匹配Alice来源、定位头有效且首次接收的图像块，包括当前发送轮次及尚未关闭的收尾轮次，也包括载荷有错误的块；不混入其他设备、已关闭轮次或重复包。无法识别的坏包和完全丢失的数据没有参与RSSI统计，“无新块”不等于射频能量为零。近1秒窗口使用电脑处理记录的时间，包含串口/队列延迟，不是连续频谱功率测量。迟到记录的RSSI也是按电脑处理时刻更新，不代表其空口到达时刻。

串口错误、电脑队列丢弃、Bob队列丢弃按每轮启动至收尾结束的观察区间统计；区间重叠时，同一异常可能在多轮中出现，不能将各轮这些计数简单相加。图像载荷、误码和每轮RSSI按会话严格分离。超过关闭期限才出现的数据不会修改已经保存的结果。

summary.json包含 rssi_samples、rssi_last_dbm、rssi_mean_dbm、rssi_min_dbm、rssi_max_dbm，便于按轮比较。无需重新烧录，关闭并重开start_demo.bat即可使用。本次多轮并行更新后10项离线测试通过，包含RSSI超时提示、跨轮连续更新、迟到数据归档以及后台保存失败停止；实际硬件效果待验证。

每轮保存在 `results/时间_会话号/`：

| 文件 | 含义 |
| --- | --- |
| source.png | 实际发送的缩放后原图 |
| received.png | 实际收到的像素和缺失区域，可独立查看 |
| received.rgb | 同一接收画面的 RGB888 原始字节，尺寸见结果记录 |
| missing_mask.png | 白色为缺失像素，黑色为已接收像素 |
| error_map.png | 红色为与原图不同的像素，绿色为一致，灰色为缺失；仅用于诊断 |
| summary.json | 提交块数、接收块数、错误位、错误像素、队列丢弃和串口错误等 |
| records.jsonl | 本轮带时间和角色的原始串口记录 |
| settings.json | 图片、尺寸、间隔、功率请求和两端身份 |

如果整轮没有收到有效图像头，就没有可靠的接收尺寸，不生成接收 PNG，`received.rgb` 为空，日志和统计仍保存。

`conditional_ber` 的分母仅为**已提交且能匹配到的已接收载荷位数**，丢包不计入 BER。停止时的缺失块可能包含尚未发送的块；同时检查 `attempted`、`api_accepted` 和 `unmatched_accepted`。`rx_state` 非零只说明设备报告异常，不把某个状态值普遍等同于特定错误原因。状态正常但载荷不一致时也会保留并提示复核。

串口命令和接收记录均有独立 CRC。出现串口校验错误、电脑/Bob 队列丢弃或设备重启时，本轮不能直接用于纯无线丢包/误码归因。

## 工程位置与环境

- `Alice/`：发送固件；`Bob/`：接收固件。
- `shared/link.c`：两端共用固件源码。
- `tools/app.py`：操作界面；`tools/protocol.py`：接收重建和统计；`tools/sender.py`：单次逐块发送。
- `demo_settings.json`：SDK、Python 和初始串口配置。
- 固定 ESP32-C5、信道 40（5.200 GHz）、20 MHz、802.11a / 6 Mbps。
- 本机环境：ESP-IDF v6.0，`C:\esp\v6.0\esp-idf`，Python `C:\Espressif\tools\python\v6.0\venv\Scripts\python.exe`。Python 需要 Pillow、pyserial 和 Tk；本机已可运行。
- 更换电脑时先修改 `demo_settings.json` 中环境路径。不要复制旧项目的构建缓存覆盖本项目。
- 如需恢复旧可靠传图功能，重新烧录 `alice_bob_oneway_5g` 对应的两端固件并启动其界面；旧项目未被本项目修改。

## 已完成的检查（2026-11-10）

### 电脑端提速更新

默认块间隔现为0 ms，采用最多4块未确认命令的流水窗口。收到Alice本机提交确认即释放窗口，不等待Bob无线确认，不进行无线重发。四条命令合计小于固件4096字节串口接收缓冲。正间隔仍使用单块确认模式。串口事件处理周期5 ms；图像仍最多约每100 ms刷新一次。仍使用文本串口协议，未改二进制协议。

停止或发生发送错误时，已经进入窗口的少量块仍可能被发送；不会自动重发。流水窗口是Alice侧待发送数据，不代表Bob必须收齐4块才能显示。Bob逐条处理接收记录，界面定时显示，仍有串口及调度延迟；没有等待整张图完成才展示。准确端到端延迟尚未测量。

第二轮提速检查：7项离线测试通过，新增窗口上限、确认释放窗口和中止测试；界面测试使用0 ms流水模式，验证错误保留和文件导出。未进行此版本的硬件测速。

新增提交耗时和近似载荷速率：`tx_ack_span_seconds` 为电脑处理首尾TX确认的时间差，`approx_payload_bps` 为已接受载荷位数除以该时间差。这是应用侧估计，非精确空口速率，不包含启动和3秒收尾；极少块时不宜据此估计吞吐量。

此次只修改电脑端程序，关闭旧窗口后重新启动即可，**已经烧录raw_image_v1的两块板无需重新烧录**。原100 ms参数仍可手动填写以复现实验。提速后的真实无线吞吐和队列压力需要硬件实测，离线测试不代表无线测速。

两端固件编译成功，没有编译器 warning/error；Alice 镜像 0xd9d90 字节，Bob 镜像 0xd8730 字节，均能放入 1 MiB 应用分区。日志在 `launcher_logs/` 和 `build_check.log`。
